# 쿠폰스탕스 인수인계 작업 문서

작성일: 2026-09-25. 상태: 소스·설정·로컬 APK, Cloud 계정 및 Play 앱 기본 상태 조회 완료. 인수자가 새 Firebase를 구축하고, 새 업로드 키도 자기 환경에서 생성·보관하는 방향으로 결정했다.

목표는 Google Play 앱과 소스·배포 자료를 인계하고, 인수자가 자신의 계정과 결제로 새 Firebase를 구축하여 운영을 재개하게 하는 것이다. 자산 인계 완료와 인수자의 서비스 재개 완료를 구분한다. 기존 운영자가 서버를 다시 운영하는 것은 현재 인계 방침에 포함하지 않으며, 이 범위는 인수자에게도 설명하고 확인받아야 한다.

AI가 이 문서를 읽고 인수를 지원할 때: 아래의 확인 사실, 예정 작업, 미확인 사항을 구분한다. `미정`인 운영자 정보·이메일·URL·보관 기간을 임의로 채우지 않는다. 코드 관련 사실은 이 체크아웃 기준이므로 인수자가 수정한 뒤에는 다시 확인한다. 작업 완료는 계획 수립이나 파일 수정만으로 표시하지 말고 각 확인표의 결과를 기록한다. 새 지원 이메일과 개인정보처리방침은 5.1~5.3절의 입력값·수정 위치·검증 절차를 따른다.

## 2. 구조와 데이터 흐름

```text
네이버 게임 라운지 공개 쿠폰 게시판
    ↓ Python 스크래퍼 (코드상 1분 간격)
Cloud Functions ──→ Firestore: processed_feeds / coupons
    ↓ Firestore users에서 알림 토큰 조회
Firebase Cloud Messaging
    ↓ 알림 수신·클릭
Flutter 앱 ──→ 게임사 쿠폰 페이지를 WebView로 표시
    ↑              ↑ 기기의 UID와 쿠폰 코드 자동 입력
Firestore 쿠폰 목록    (실제 쿠폰 등록은 게임사 서비스가 처리)
```

| 위치 | 역할 / 인수자가 알아야 할 내용 |
| --- | --- |
| `mobile/lib/main.dart` | Firebase·FCM 초기화, 로컬 UID를 읽어 시작 화면 결정 |
| `mobile/lib/presentation/` | UID 등록, 쿠폰 목록, 설정, WebView 화면과 Riverpod 상태 관리 |
| `mobile/lib/domain/` | UID·쿠폰 관련 유스케이스와 저장소 인터페이스 |
| `mobile/lib/data/` | Firestore 통신, FCM 토큰 등록, 로컬 저장 |
| `functions/main.py` | 현재 Firebase source 설정에서 사용하는 배포 진입점 |
| `functions/src/main.py` | 별도의 수정본. 진입점과 기능이 달라 그대로 혼동하면 안 됨 |
| `functions/src/scraper/coupon_scraper.py` | 네이버 JSON API에서 오늘 게시물의 쿠폰 코드 추출 |
| `functions/src/services/` | Firestore 기록·정리와 FCM 전송 |
| `firebase/` | Firestore 규칙과 인덱스 설정 |
| `배포용리소스/` | APK, AAB, 아이콘, 스크린샷 4장 |
| `docs/`, `CLAUDE.md`, `README.md` | 개발 당시 기록. 실제 코드와 맞지 않는 설명이 있어 참고 자료로 사용 |

배포 진입점 판단은 `firebase.json`의 `source: functions`와 Firebase Python의 `main.py` 구조를 기준으로 했다. 실제 과거 배포물이 이 체크아웃과 같았는지는 별도 확인이 필요하다. [Firebase 함수 프로젝트 구조](https://firebase.google.com/docs/functions/get-started?gen=2nd)

데이터는 다음과 같이 구분한다.

| 데이터 | 실제 저장·전달 위치 | 이전 시 의미 |
| --- | --- | --- |
| 게임 UID | `flutter_secure_storage`로 기기에 저장. 쿠폰 등록 시 게임사 페이지에 입력 | 현재 코드에서는 Firestore에 저장하지 않음. 기기 내부 데이터 보존과 업데이트 검증 필요 |
| 알림 토큰 | Firestore `users`: `fcm_token`, `created_at`, 선택적 `updated_at` | 새 Firebase로 옮기면 새 프로젝트의 토큰을 다시 등록해야 함 |
| 쿠폰 이력 | Firestore `coupons` | 정리 함수는 14일 보관하도록 작성됨. 삭제된 데이터의 복구·백업 여부는 미확인 |
| 중복 발송 방지 기록 | Firestore `processed_feeds` | 정리 함수는 7일 보관하도록 작성됨. 새 DB에서 수집을 시작할 때 재알림 범위 결정 필요 |
| 테마·쿠폰 확인 표시 | 기기 `SharedPreferences` | 서버에서 일괄 이전할 대상이 아님 |

외부 의존 서비스는 네이버 쿠폰 게시판과 게임사 쿠폰 등록 사이트다. 이 서비스들의 계정·소유권을 이전하는 구조는 아니다. 네이버 응답 형식과 게임사 입력 필드 변경은 인수자가 계속 대응해야 한다.

## 3. 확정 방침: 인수자 소유 Firebase에 새로 구축

[Google Cloud 리소스 관리](https://console.cloud.google.com/cloud-resource-manager)의 활성 목록과 삭제 대기 리소스에 `trickcal-coupon-notifier`가 없었고, Firebase 직접 접근도 불가능했다. 사용자가 기존 관리 계정임을 확인했으며 새 구축 방침에 동의했다. 기존 Firebase 복구나 기존 운영자의 결제 재연결은 진행하지 않는다.

인수자는 새 프로젝트 ID를 정한다. 기존 ID는 과거 연결을 추적하는 참고 정보로 남기며 재사용을 전제로 하지 않는다. Google Cloud의 영구 삭제된 프로젝트 ID는 재사용할 수 없다. [공식 삭제·복구 안내](https://docs.cloud.google.com/resource-manager/docs/delete-restore-projects)

| 구분 | 인계 범위 |
| --- | --- |
| 넘기는 자산 | 기존 Google Play 앱, 현재 소스와 보유 배포 자료, 설정 설명, 알려진 문제, 확보되는 서명 자료 |
| 현재 넘길 수 없는 것 | 살아 있는 기존 Firebase 백엔드와 확인되지 않은 과거 DB·알림 토큰. 백업이 없는 데이터를 전달할 수 있다고 약속하지 않음 |
| 인수자가 수행 | 새 Firebase 생성·결제·보안 설정, 백엔드 배포, 앱 연결 변경과 토큰 등록 수정, 업데이트·사용자 안내·운영 |

프로젝트 전체가 삭제된 상태라면 기존 앱의 새 쿠폰 조회·알림 발송·초기 토큰 등록은 정상 동작을 기대하기 어렵다. 일부 기기에는 로컬 UID나 캐시된 쿠폰이 남아 있을 수 있다. Play 소유권만 이전해도 이 기능들이 자동 복구되지는 않는다.

인수자가 수행할 필수 작업:

1. 인수자가 새 프로젝트 ID, 소유 계정, 결제 주체, 리전과 운영 담당자를 결정한다. Cloud Functions 배포에는 Blaze 요금제가 필요하다. [Firebase 배포 요건](https://firebase.google.com/docs/functions/get-started?gen=2nd)
2. Android 앱을 **동일한 패키지명**으로 Firebase에 등록한다. `.firebaserc`, `mobile/firebase.json`, `mobile/lib/firebase_options.dart`, `mobile/android/app/google-services.json`을 일관되게 갱신한다.
3. 아래 재가동 전 문제를 해결하고 Firestore·Functions·Scheduler·FCM을 구성한다. 기존 데이터는 백업이 실제로 발견된 범위만 복원한다.
4. 기존 설치 사용자의 새 프로젝트 토큰 등록을 구현·검증한다. 현재 토큰 등록은 UID 설정/저장 흐름에 있고, 일반 시작 흐름은 UID만 읽는다. 토큰 갱신 리스너도 제공되지만 호출 연결을 찾지 못했다. 설정 파일 교체만으로는 충분하지 않다.
5. Play에 올라간 모든 버전보다 높은 versionCode로 AAB를 만들고, 기존 설치본에서 업데이트했을 때 UID 유지·토큰 재등록·쿠폰 조회·알림 클릭을 확인한다.
6. 구버전은 삭제된 Firebase를 계속 가리키므로 업데이트하지 않은 사용자는 정상화되지 않을 수 있음을 안내한다. 기존 알림 경로가 없어졌다면 Play 등록정보나 기존 공지 채널로 알린다.

현재 확정된 것은 기존 운영자의 인계 방침이다. 인수자에게 서버 부재·재구축 책임·데이터 상태를 설명하여 수락 여부를 확인해야 한다. 새 계정 생성·결제 연결·배포는 아직 수행하지 않았다.

| 스토어 자산 | 설명, 아이콘, 스크린샷, 그래픽 원본, 번역, 개인정보처리방침 URL와 편집 권한 | 일부 이미지 있음, Console 자료 필요 |
| 연락·운영 기록 | 사용자 문의 창구, 장애 이력, 정책 경고, 게임사/네이버와 주고받은 허용·중단 요청이 있다면 기록 | 소스에 기존 개인 문의 주소가 남아 있음 |
| 권리 범위 | 코드·이름·아이콘 등 넘길 권리와 제3자 자산의 출처·사용 조건 | README는 MIT 표기, LICENSE 파일은 없음. 실제 허락 범위 확인 필요 |
| 종료 조건 | 운영 책임·비용 부담 전환일, 인계 후 지원 범위와 종료일, 기존 접근 권한 회수 시점 | 쌍방 합의 필요 |

개인 Google 계정 비밀번호나 개인 결제수단을 넘기는 방식으로 처리하지 않는다. 앱 이전과 필요한 서비스의 권한 인계를 사용한다. 서명 비밀정보는 이 문서나 Git에 적지 않고 별도의 안전한 경로로 전달한다. Firebase 클라이언트 설정 파일과 서버 관리자 자격증명은 서로 다른 자료다.

이 앱은 Play 앱 서명을 사용한다. Google이 관리하는 실제 앱 서명 키와 개발자가 AAB 업로드에 사용하는 키를 구분한다. 기존 업로드 키는 분실한 것으로 보고 새 키를 마련한다. 인수자는 앱 이전 후 업로드 키 재설정을 신청할 수 있다. 새 keystore 생성만으로는 부족하며 Console의 재설정 반영이 필요하다. [Google Play 앱 이전의 서명 안내](https://support.google.com/googleplay/android-developer/answer/6230247?hl=ko)

새 업로드 키는 인수자가 자기 환경에서 생성하고 보관하기로 결정했다. 기존 운영자나 이 작업 환경에서는 새 개인 키를 만들거나 전달받지 않는다. 다음 순서로 준비한다.

1. 인수자가 자신의 환경에서 새 업로드 keystore를 생성하고 키 파일·alias·비밀번호·백업을 관리한다. 키 생성 자체는 앱 이전 전에도 준비할 수 있다.
2. 새 키의 공개 인증서를 PEM 형식으로 내보낸다.
3. 앱 이전이 완료되면 인수자 Play Console의 앱 서명 화면에서 업로드 키 재설정을 신청하고 공개 인증서를 제출한다.
4. 재설정 반영과 새 인증서 지문을 Console에서 확인한 뒤 새 키를 릴리스 빌드에 사용한다. 기존 업로드 인증서 지문은 과거 기록으로 보존한다.
5. 인수자가 로컬 `mobile/android/key.properties`에 새 키 경로·alias·비밀번호를 설정하고, 새 AAB 업로드를 검증한다. 키와 비밀번호 파일은 Git에 포함하지 않는다.

업로드 키 재설정은 Google이 관리하는 앱 서명 키를 바꾸지 않으므로 기존 Play 앱의 업데이트 경로를 유지할 수 있다. 새 키 생성과 재설정은 아직 실행하지 않았다. [Android 업로드 키 재설정 안내](https://developer.android.com/studio/publish/app-signing#reset_upload_key)

2026-09-25 [Play 앱 서명 화면](https://play.google.com/console/u/0/developers/6078105117589181989/app/4973167590751734299/keymanagement)에서 읽은 공개 인증서 지문:

| 구분 | SHA-256 |
| --- | --- |
| 앱 서명 인증서(Digital Asset Links 영역) | `F7:6A:F1:F9:DE:2A:D2:EE:F1:C1:83:2D:BB:FE:A9:40:F6:06:B1:C7:5C:CF:D7:F3:28:6C:EF:BD:00:A4:6B:8C` |
| 업로드 인증서 | `E2:88:9C:AD:9D:E1:8D:9C:34:7D:AB:8C:CC:2C:88:FE:AB:0B:4C:5C:00:F5:CB:90:46:98:35:71:34:C8:96:EC` |

이 지문은 개인 키가 아니며 AAB 서명에 사용할 수 없다. Console에 `Request upload key reset` 메뉴가 존재하는 것만 확인했고, 신청·키 교체는 하지 않았다.

상대가 정하면 반영할 운영 정보는 새 지원 이메일과 개인정보처리방침 URL·관리 주체다. 기존 URL은 가능한 범위에서 Console에서 먼저 확인한다. 이 정보가 아직 없어도 조사와 전달 자료 준비는 진행할 수 있다. 새 Firebase 프로젝트 ID·리전·결제정보·업로드 개인 키는 인수자의 구축·운영 사항이며, 현재 인계 준비를 위해 이 작업에 제공할 필요가 없다.

새 개인 개발자 계정에는 테스트·게시 접근 요건이 적용될 수 있다. 기존 앱 이전에 어떤 요건이 적용되는지는 대상 계정의 Console과 이전 절차에서 확인해야 하며, 신규 앱의 테스트 일정을 그대로 확정하지 않는다. [새 개인 개발자 계정의 테스트 안내](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ko)

### 5.1 지원 이메일·개인정보처리방침 작업의 입력값

인수자가 자기 명의의 지원 창구와 개인정보처리방침을 새로 마련한다. 인수자가 확정한 값을 인수자 또는 인수자를 돕는 AI가 이 표에 기록한다. 기존 운영자가 대신 결정하거나 새 계정을 만들 필요는 없다. 현재는 안내만 작성했으며 이메일 개설·개인정보처리방침 생성·웹 게시·Console 변경은 수행하지 않았다.

| 입력값 | 현재 값 / 결정 기준 |
| --- | --- |
| 앱 이름 | `쿠폰스탕스` — 방침에 명시하고 Play 등록정보와 대응되게 작성 |
| `OPERATOR_NAME` | 미정. 인수 후 실제 운영 책임을 지는 개인/조직과 개발자 표시 이름 |
| `SUPPORT_EMAIL` | 미정. 인수자가 관리하며 실제 문의를 받고 답변할 수 있는 공개 주소. 개인정보 문의에도 사용할지 결정 |
| `PRIVACY_POLICY_URL` | 미정. 최종 방침을 공개 게시한 웹페이지 주소. 생성기 주소나 편집 화면 주소가 아님 |
| 게시 위치·관리자 | 미정. 인수자 계정의 Notion 또는 Google Sites 등. 지속적으로 수정·게시할 담당자 지정 |
| 시행일·보관·삭제 정책 | 미정. 실제 전환 일정, 데이터별 보관 기간/삭제 조건, 삭제 요청 처리 방법을 인수자가 정하고 구현과 대조 |

이 표의 이름은 작업 중 값을 구분하기 위한 표기이며, 현재 앱에 같은 이름의 환경변수나 설정 항목이 있다는 뜻은 아니다. 미정 값은 초안에만 표시하고 공개 문서나 배포 앱에는 남기지 않는다.

### 5.2 새 지원 이메일 반영 순서

1. 인수자가 공개할 주소를 정하고 수신·회신 가능 여부를 확인한다. Google 로그인용 주소와 같을 필요는 없다. 메일함 비밀번호는 인계 문서나 소스에 넣지 않는다.
2. Play Console에서 해당 앱의 **Grow users → Store presence → Store settings → Contact details**에 새 이메일을 입력한다. 앱 지원 이메일은 필수이며, 개발자 계정의 관리 연락처를 바꾸는 것과 별개다. 실제 화면의 저장·검토/게시 절차를 완료하고 스토어에 표시된 값을 확인한다. [Play 앱 연락처 안내](https://support.google.com/googleplay/android-developer/answer/9859152?hl=en)
3. `mobile/lib/presentation/pages/settings_page.dart`의 **문의하기** 주소와 `mobile/lib/core/constants/disclaimer_text.dart`의 **문의** 주소를 변경한다. 현재 두 곳의 값은 `nicker.erasers_3y@icloud.com`이다. 설정 화면의 문의 버튼은 현재 준비 중 메시지만 표시하므로, 메일 작성 화면 열기나 주소 복사 등 실제 문의에 사용할 동작도 구현·확인한다.
4. 새 개인정보처리방침의 연락처에도 같은 값을 반영한다. 별도의 개인정보 문의 주소를 선택했다면 용도를 명확히 구분한다. `rg -n 'nicker\.erasers_3y@icloud\.com' mobile`로 앱 소스에 기존 주소가 남았는지 검사하고 새 앱 화면·스토어·게시 문서를 대조한다. 이 인계 문서의 과거 기록까지 새 값으로 덮어쓰지는 않는다.

완료 기록: 새 주소, 수신·회신 확인일, 앱 수정 파일, Play 반영 확인일. 메일 발송이나 Console 변경은 해당 작업을 맡은 인수자가 수행한다.

### 5.3 개인정보처리방침 초안 작성 → 공개 게시 → 앱·Play 반영

**초안 작성:** [App Privacy Policy Generator](https://app-privacy-policy-generator.firebaseapp.com/)를 활용한다. `Start`에서 `App Name`에는 앱 이름, `Contact Information`에는 확정한 문의 주소를 넣는다. 템플릿과 이후의 운영 형태·사용 서비스 항목은 실제 재구축 결과에 맞춰 선택한다. 이 생성기는 제3자 초안 작성 도구이며 생성 결과 자체가 Google의 승인이나 정책 준수를 보장하지 않는다. 영문 초안을 사용하면 한국어 사용자도 이해할 수 있도록 내용을 검토·정리한다.

인수자의 AI는 생성 결과를 그대로 게시하지 말고 다음 코드 근거와 대조하여 보완한다. 아래는 현재 소스에서 확인한 출발점이며, 새 구현이 달라지면 그에 맞춰 수정한다.

| 항목 | 초안에 반영하거나 확인할 내용 |
| --- | --- |
| 게임 UID | `mobile/lib/data/datasources/local/uid_storage.dart`에서 기기에 저장. 현재 Firestore에는 저장하지 않지만 쿠폰 등록 시 게임사 WebView 페이지에 입력·제출되므로 “어느 서버에도 전송하지 않음”이라고 쓰지 않음 |
| 푸시 알림 | Firestore `users`에 FCM 토큰과 등록/갱신 시각을 저장하여 알림에 사용. `firebase_messaging` 등 실제 SDK 버전의 자동 처리 데이터도 확인. 토큰을 쓴다는 사실을 누락하거나 “개인정보를 전혀 수집하지 않음”으로 일괄 선언하지 않음 |
| 삭제·보관 | 현재 설정의 UID 삭제는 기기 UID만 삭제하며 서버 알림 토큰까지 지우는 기능은 아님. 토큰 보관·삭제 조건과 요청 처리 방법을 정하고 구현. 쿠폰 14일·중복 기록 7일 정리 규칙을 사용자 토큰의 보관 기간으로 잘못 기재하지 않음 |
| 외부 서비스·문의 | Firebase의 저장·알림 처리, 게임사 쿠폰 페이지로의 전달, 네이버 공개 쿠폰 수집의 역할을 구분. WebView의 쿠키·로그와 문의 이메일로 받는 정보도 실제 동작·운영 방식에 맞춰 확인 |
| 사용하지 않는 기능 | 현재 Flutter 선언 의존성에서 광고·인앱결제·Analytics·Crashlytics SDK를 찾지 못함. Firebase를 쓴다는 이유만으로 이들을 선택하지 않으며, 새로 도입하면 문서와 Play 선언에 반영 |

SDK의 데이터 항목은 [Firebase의 Play 데이터 공개 안내](https://firebase.google.com/docs/android/play-data-disclosure)를 재확인한다. `mobile/lib/core/constants/disclaimer_text.dart`의 기존 개인정보 문구도 새 방침과 일치하게 수정한다. 데이터 접근을 제한한다고 설명하려면 7절의 Firestore 규칙 문제 등 실제 구현도 먼저 해결해야 한다.

**내용 확정:** 제목을 개인정보처리방침으로 명시하고 앱·운영 주체·문의 창구, 처리 데이터와 목적·전달 대상, 보안 조치, 보관·삭제 방침, 시행일을 정리한다. 아직 구현하지 않은 삭제 기능이나 확인하지 않은 보안 조치를 제공한다고 쓰지 않는다. 공개 URL은 로그인·지역 제한 없이 열리고 방문자가 편집할 수 없는 웹페이지여야 하며 PDF로 대체하지 않는다. [Google Play 사용자 데이터 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)

**공개 게시:** 다음 중 하나만 선택하면 된다. 인계 문서 전체를 공개하지 말고 개인정보처리방침만 별도 페이지로 만든다.

| 방법 | 게시와 URL 확보 |
| --- | --- |
| Notion | 인수자 소유 페이지에 최종 내용을 작성하고 `Share → Publish → Publish`로 웹에 게시. 게시된 사이트를 열어 URL 복사. 방문자는 열람만 가능하게 하고 내부 페이지 링크와 혼동하지 않음. [Notion 게시 안내](https://www.notion.com/help/public-pages-and-web-publishing) |

브라우저의 로그아웃 상태/시크릿 창과 휴대전화에서 최종 URL을 열어 본문·연락처·시행일이 읽히는지 확인한다. 원문과 편집 권한은 인수자가 보관하고, 게시 주소를 변경하면 앱과 Play의 링크도 함께 갱신한다.

**앱·Play 반영:**

1. 최종 공개 URL을 5.1절의 `PRIVACY_POLICY_URL`에 기록한다. 생성기 URL을 대신 넣지 않는다.
2. Play Console의 **Policy and programs → App content → Privacy Policy → Start/Manage**에서 이 URL을 입력하고 저장한다. 현재 화면에서 요구하는 검토·게시 절차까지 확인한다. [Play 개인정보처리방침 등록 안내](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en)
3. 앱 설정에 **개인정보처리방침** 항목을 추가하여 동일한 공개 URL을 열 수 있게 한다. 현재 설정에는 면책 조항 이동만 있어 별도 방침 링크 구현이 필요하다. 지원 이메일 변경과 함께 새 버전에서 검증한다.
4. Play의 **Data safety(데이터 보안)** 답변도 새 앱·SDK·서버의 실제 처리와 대조하여 갱신한다. 개인정보처리방침 링크를 바꾸는 것만으로 이 답변이 자동 수정되지는 않는다. 데이터 종류와 수집·공유 여부를 추측으로 선택하지 않는다.

완료 기록: 최종 공개 URL, 운영자·관리자, 시행일, 비로그인 열람 확인일, 앱에서 링크 확인한 버전, Play 반영 상태, 남은 미확인 항목. 새 방침을 담은 앱 업데이트가 기존 구버전의 내장 문구까지 바꾸지는 않는다는 점도 운영 안내에 고려한다.

## 6. Google Play 이전 절차에서 챙길 범위

두 개발자 계정이 등록·활성 상태여야 하고 원래 계정과 앱의 정책 상태를 확인해야 한다. 양쪽 등록 거래 ID를 준비하고 기존 운영자가 이전을 요청하면 대상 개발자가 검토·승인한다. 등록정보·평점·리뷰 등은 이전되지만 통합 서비스의 권한·연결은 별도 처리 대상이다. 필요한 과거 보고서는 미리 내려받고 테스트 그룹은 다시 구성할 준비를 한다. Firebase와 Play의 연결이 남아 있다면 기존 연결 해제와 대상 계정 연결도 확인한다. [공식 앱 이전 안내](https://support.google.com/googleplay/android-developer/answer/6230247?hl=ko)

현재 소스에서는 광고·인앱결제 SDK를 찾지 못했고 면책 문구도 무료·무광고 운영을 설명한다. 실제 Play의 유료 설정·상품 존재 여부까지 확인한 것은 아니다. 발견되면 결제 프로필과 정산·주문 처리 항목을 추가한다.

조회 당시 앱 목록의 게시 상태는 `Unpublished`였다. [릴리스 화면](https://play.google.com/console/u/0/developers/6078105117589181989/app/4973167590751734299/releases/overview)에는 기존 운영·Alpha 릴리스가 활성 상태로 표시된다. 앱의 게시 상태와 기존 릴리스의 활성 상태를 구분해 기록하며, 활성 릴리스가 있다는 이유로 신규 사용자가 현재 앱을 설치할 수 있다고 판단하지 않는다.

## 8. 개발 환경·배포 자료의 상태

서비스 재개 완료 확인표(인수자 담당):

- [ ] 인수자 소유·결제로 새 Firebase를 구성하고 서버 데이터 초기화·복원 범위를 기록했다.
- [ ] 인수자가 생성한 새 업로드 키의 재설정 반영과 백업을 확인했다.
- [ ] 동일 패키지의 새 AAB를 인수자 계정에서 업로드할 수 있다.
- [ ] 기존 설치본 업데이트 후 UID 유지, 새 토큰 등록, 쿠폰 조회가 확인된다.
- [ ] 지정된 테스트 기기에서 전경·백그라운드·종료 상태의 알림과 클릭 이동이 확인된다.
- [ ] 네이버 수집, 중복 방지, 게임사 페이지 자동 입력이 확인된다.
- [ ] 새 지원 이메일의 수신·회신과 앱 문의 동작을 확인하고 앱·스토어·개인정보처리방침에 반영했다(5.2절).
- [ ] 새 개인정보처리방침을 공개 게시하고 비로그인 열람·앱 링크·Play URL을 확인했다. 데이터 보안 선언과 실제 구현도 일치한다(5.3절).
- [ ] 게시 중지된 앱의 재게시와 사용자 대상 서비스 재개 안내를 완료했다.
- [ ] 인수자가 배포·로그 확인·장애 대응·비용 확인을 자신의 권한으로 할 수 있다.
- [ ] 남은 운영 문제의 담당자와 대응 일정이 정해졌다.

아직 실제 앱 이전, 계정 생성, Firebase 복구, 데이터 이동, 코드 수정, 배포는 진행하지 않았다.
